## Observations

- `to-spec` synthesizes already-decided work; it is not an interview.
- It is intended mainly for multi-session work; single-session work can skip directly to implement.
- Before writing prose it proposes and confirms test seams.
- The spec is a snapshot/decision record, not a durable forever-updated artifact.
- It publishes to the configured issue tracker and uses `ready-for-agent`, which can confuse AFK runners into treating the parent spec as executable work.
- It does not search for overlapping tracker work or link ADRs it respects.
- Large tracker-hosted specs can truncate; docs recommend keeping to-spec and to-tickets in the same context window.
